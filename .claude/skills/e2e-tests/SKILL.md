# End-to-end tests

The suite lives in `tests/e2e/` and runs against the real, deployed app
(`https://npohle.github.io/everone/`), served locally over TLS via Caddy and
signed in with a real Microsoft account. There's no mocking.

## Running the suite

```bash
npm run test:e2e
```

That's it — don't start a dev server and don't drive sign-in by hand first.
Both are already handled inside the suite itself:

* `global-setup.ts` starts a dedicated Caddy instance serving the repo root
  before any test runs, and `global-teardown.ts` stops it after.
* The `auth` Playwright project (`00-auth.setup.ts`) signs in for real via the
  Microsoft OAuth popup flow (username, password, TOTP) and saves the
  resulting storage state, before the `e2e` project (everything else) runs.
* Every other spec's `page`/`context` fixture (`tests/e2e/fixtures.ts`) loads
  that saved storage state automatically, so specs start already signed in.

Run a single spec file the normal Playwright way:

```bash
npx playwright test 02-search.spec.ts
```

Requires `.env` at the repo root with `TEST_USERNAME`, `TEST_PASSWORD`,
`TEST_TOTP_SEED` (already set up in this repo — never print or log these
values) plus `caddy` and `oathtool` installed locally; see
[tests/README.md](../../../tests/README.md) for full setup details if a run
fails for environment reasons.

## Where output goes

Each run gets its own folder, `tests/artefacts/<RUN_ID>/` (gitignored), where
`RUN_ID` is generated by the `test:e2e` npm script. It holds:

* Screenshots each spec takes (see naming convention below).
* `localstorage.json` / `sessionstorage.json` — the signed-in state captured
  by the `auth` project.
* Playwright's own trace files (`trace: 'retain-on-failure'`), useful for
  debugging a failing run with `npx playwright show-trace`.

After a run, find the newest directory under `tests/artefacts/` to inspect
what happened.

## Sharing a run's artefacts in a PR description

`tests/artefacts/<RUN_ID>/` only exists on the machine that ran the suite, so
a PR description can't link to it directly. If a PR's changes are backed by
an e2e run and it's worth linking the artefacts (screenshots, traces) from
the PR description, upload that run's folder to the shared `dufs` file
server with `rclone`, then link to it there — do this on request, not as a
standing rule for every PR.

```bash
RUN_ID=$(ls tests/artefacts | sort | tail -n1)
rclone copy "tests/artefacts/$RUN_ID" \
  ":webdav,url='http://dufs-service.default.svc.cluster.local/dufs/tasks',vendor=other:$RUN_ID" \
  --exclude "localstorage.json" --exclude "sessionstorage.json"
```

Notes:

* `:webdav,url='...',vendor=other:$RUN_ID` is an rclone on-the-fly remote
  (dufs speaks WebDAV) — no saved `rclone.conf` remote needed. The trailing
  `:$RUN_ID` is the destination path, so the run lands in its own
  `$RUN_ID` subdirectory on the server, matching the local folder name.
* Always exclude `localstorage.json` / `sessionstorage.json` from the
  upload — they hold the real, live Microsoft sign-in state for the test
  account (cookies / session tokens), not just test output.

The uploaded run is then reachable at:

```
http://ubuntu-nbg1-1.tailab4759.ts.net/dufs/tasks/<RUN_ID>/
```

Only include that link in a PR description when asked to, or when the PR
description is explicitly about this e2e run's results.

## Writing a new spec

Follow the existing specs' conventions exactly — look at
[02-search.spec.ts](../../../tests/e2e/02-search.spec.ts) as a template:

* File name: `NN-topic.spec.ts` (two-digit prefix, ordered — auth is `00`,
  existing specs go up from `01`; pick the next free number for a new file,
  or add a test to an existing file if it's the same topic).
* Import `test`/`expect` from `./fixtures.ts`, never directly from
  `@playwright/test` — that's what wires up the signed-in `context`/`page`.
* Test title: `"TOPIC-NNN: description"` (e.g. `"SEARCH-002: ..."`) — the
  prefix matches the file's topic, numbered per file.
* Read `process.env.ARTEFACTS_DIR` for screenshot paths, named
  `NN-MM-description.png` (file prefix, then a per-test sequence number).
* Navigate with `await page.goto("https://npohle.github.io/everone/")` — the
  real hostname, resolved locally by Caddy via the `browser` fixture's
  `--host-resolver-rules`, not `localhost`.
* Assert the app has finished loading before asserting on content:
  `await expect(page.getByText("Loading")).not.toBeVisible()`.

```ts
import { test, expect } from "./fixtures.ts";

test("TOPIC-001: description", async ({ page }) => {
  const artefactsDir = process.env.ARTEFACTS_DIR;

  await page.goto(`https://npohle.github.io/everone/`);
  await expect(page.getByText("Loading")).not.toBeVisible();
  await page.screenshot({ path: `${artefactsDir}/NN-00-start.png` });

  // ... interact with the page, then assert ...
});
```

## Finding selectors while writing a test

To poke around the real, signed-in app UI and figure out what selector or
locator to write into a new spec, don't spin up the e2e suite for that —
open an interactive, pre-authenticated session instead, per the
`authenticated-browser-session` skill.
